# ТЗ: неизменяемость маршрута после заявки, фильтр по удалению, отложенный пробег по странам

## Правила языка документа
- Основной язык: **RU** (термины API/кода: английский по принятому в проекте стиле).
- Связанные документы: `docs/specs/routes-server-workflow-and-freight-quoting.md`, `docs/specs/freight-cost-scenario-nbu-pricing.md`, `docs/specs/route-point-operations-rules.md`, `docs/system.md`.

## Контекст UI (актуальный роутинг)
В актуальном приложении (`frontend/src/app/app.routes.ts`) нет отдельных URL под старые сценарии вроде выделенной «истории маршрутов» или `freight-calculation` как отдельной страницы. Требования по UX из §8 реализуются на **существующих** экранах и в shared-компонентах:

| Путь | Назначение |
|------|------------|
| `/route-builder` | Построение и редактирование маршрута (`RouteBuilderComponent`). |
| `/routes` | Список сохранённых маршрутов пользователя, удаление, диалог заявки на фрахт (`RoutesComponent`). |
| `/my-freight-requests` | Список заявок текущего пользователя (`MyFreightRequestsComponent`). |
| `/admin/route-requests` | Очередь заявок для ADMIN/MANAGER (`AdminRouteRequestsComponent`). |

Общие диалоги: `RouteFreightRequestDialogComponent`, `RouteDeleteConfirmDialogComponent` (под `frontend/src/app/shared/components/`).

Если в репозитории остаются компоненты **без** записи в `app.routes.ts`, они **не** считаются источником требований до подключения к роутингу.

## 1. Цель
1. Зафиксировать **юридически и операционно значимый снимок маршрута** на момент отправки заявки на расчёт фрахта: после создания `RouteRequest` исходный `Route` **нельзя изменять**; для правок пользователь получает **новую копию маршрута** с новым `id`.
2. На экране списка маршрутов (в первую очередь **`/routes`**) обеспечить просмотр **не удалённых**, **удалённых** (soft delete) и **всех** маршрутов владельца с явной семантикой фильтров; владелец может **восстановить** удалённый маршрут и снова сделать его **активным** (не удалённым) в рамках своих прав.
3. При **создании заявки на фрахт** (`POST /api/v1/route-requests`) **не выполнять** расчёт пробега по странам и не сохранять `route_country_distances` / аналог; этот расчёт выполняется **позже** (отдельным шагом в админском/менеджерском контуре расчёта — см. §6).

## 2. Термины
| Термин | Значение |
|--------|----------|
| `Route` | Сохранённый snapshot маршрута, владелец — пользователь. |
| `RouteRequest` | Заявка на расчёт фрахта, ссылается на `routeId`. |
| **Заблокированный маршрут** | `Route`, по которому уже существует хотя бы одна `RouteRequest` (в любом статусе, если иное не согласовано в §7.1). |
| **Не удалённый** | Запись маршрута без soft delete (`deletedAt IS NULL` / `isDeleted=false` — по фактической схеме проекта). |
| **Удалённый** | Soft delete: поле удаления установлено; маршрут не показывается в списке по умолчанию, но доступен при фильтре «удалённые». |
| **Активный** (в смысле списка) | Синоним **не удалённого**: маршрут снова попадает в `view=active` после восстановления. |

## 3. Функциональные требования

### 3.1 Неизменяемость маршрута после заявки
1. После успешного **`POST /api/v1/route-requests`** с телом `{ "routeId": "<id>" }` маршрут `<id>` переходит в состояние **immutable (read-only)** для операций изменения геометрии/точек/полилинии/основных полей snapshot.
2. Запрещённые операции для заблокированного маршрута (минимальный набор; расширять по мере появления полей редактирования):
   - `PUT`/`PATCH` маршрута, меняющие точки, polyline, `distanceKm`, `durationMin`, профиль маршрутизации и любые поля, влияющие на трассу или расчёт длины.
   - Любой внутренний endpoint «пересчитать маршрут» для этого `routeId`.
3. При попытке изменения — ответ **`409 Conflict`** (или **`422`**) с кодом бизнес-ошибки, например `ROUTE_LOCKED_BY_REQUEST`, и человекочитаемым сообщением (i18n на фронте).
4. **Дублирование для редактирования:** если пользователь хочет изменить маршрут, с которым уже связана заявка:
   - вызывается операция **`POST /api/v1/routes/my/{id}/duplicate`** (или эквивалент с тем же контрактом);
   - сервер создаёт **новый** `Route` с новым `id`, копией snapshot и метаданных, **в состоянии «не удалённый»**, без связи с старыми `RouteRequest`;
   - владелец — тот же пользователь;
   - опционально: автоматический суффикс к `title` (например, «(копия)») или копия title 1:1 — **зафиксировать в реализации один вариант**;
   - дальнейшее редактирование выполняется только над **новым** `id` (типичный переход: **`/route-builder`** с `id` нового маршрута).
5. Чтение (`GET`), список, просмотр в связке с заявкой — **без ограничений** для владельца (и admin/manager по существующим правилам), с учётом soft delete и фильтров §3.2.

### 3.2 Список маршрутов и фильтры (только удалён / не удалён)
1. `GET /api/v1/routes/my` принимает query-параметр **`view`** (или `filter`):
   | Значение | Поведение |
   |----------|-----------|
   | `active` (дефолт) | Маршруты владельца **не** soft-deleted. |
   | `all` | Все маршруты владельца: и **не удалённые**, и **удалённые**. |
   | `deleted` | Только soft-deleted. |
2. Для `deleted` (и при необходимости для `all` в части удалённых) допускается ограниченный набор полей в ответе (без тяжёлой геометрии), если нужно для производительности — указать в OpenAPI.
3. **Восстановление (обязательно в v1):** владелец может вернуть маршрут в **активное** состояние (снять soft delete). После восстановления маршрут снова виден в `view=active` и участвует в обычном workflow (открытие **`/route-builder`**, дублирование при блокировке и т.д.). Правила **неизменяемости** после `RouteRequest` **сохраняются**: восстановление **не** снимает блокировку редактирования snapshot.

### 3.3 Отложенный расчёт пробега по странам при создании заявки
1. **`POST /api/v1/route-requests`** не инициирует вызов HERE / не пишет breakdown по странам, не ставит фоновые задачи на country breakdown для этого события.
2. Расчёт пробега по странам выполняется **только** при явном действии admin/manager: `POST /api/v1/admin/route-requests/{id}/country-breakdown` (см. `docs/system.md`).
3. В `routes-server-workflow-and-freight-quoting.md` требования синхронизированы: автоматический расчёт при создании заявки **не** предполагается; источник истины по таймингу — данный документ.

## 4. Модель данных (миграция Flyway)
1. Soft delete для маршрутов — **как уже в проекте** (`deleted_at` / `is_deleted`); отдельных полей «архив» **не** вводить.
2. Индекс для списков: составной **`(user_id, deleted_at)`** (или эквивалент по схеме) — уточнить после EXPLAIN.
3. Таблица связи «маршрут заблокирован»: либо **денормализация** `routes.locked_at` / `routes.has_route_request` при создании первой заявки, либо проверка `EXISTS (SELECT 1 FROM route_requests WHERE route_id = ?)` в сервисе. Рекомендация: **без денормализации** в v1 при малом объёме; при нагрузке — кэш флага на `routes`.

## 5. API (черновик контракта)

### 5.1 Дублирование маршрута
- **`POST /api/v1/routes/my/{id}/duplicate`**
  - Auth: владелец маршрута (`USER` и выше по правилам сохранения маршрутов).
  - Ответ **`201`**: тело как у `POST /api/v1/routes` при создании (новый `id`).
  - Ошибки: `404`, `403`, `409` если маршрут удалён и дублирование запрещено политикой (зафиксировать: **разрешить** дублирование удалённого — нет, только неудалённые).

### 5.2 Список с фильтром
- **`GET /api/v1/routes/my?view=active|all|deleted`**
  - Дефолт: `active` (только не удалённые).
  - Пагинация: как в текущем API (`page`, `size`) — сохранить обратную совместимость.

### 5.2.1 Восстановление маршрута
- **`POST /api/v1/routes/my/{id}/restore`**
  - Auth: владелец маршрута.
  - Действие: снять soft delete (очистить `deletedAt` / `isDeleted=false` — по схеме проекта).
  - Ответ **`200 OK`**: тело — актуальный DTO маршрута в **не удалённом** состоянии (как после `GET .../my/{id}`).
  - Если маршрут **уже не удалён** — **`200 OK`** + тот же DTO (**идемпотентность**, см. закрытие §7.3).
  - Ошибки: `404` (нет маршрута или не владелец по политике `404/403`), `403`.
  - Альтернатива контракту: **`PATCH /api/v1/routes/my/{id}`** с `{ "deleted": false }` — только если унифицируют с другими PATCH-полями; предпочтительно отдельный `POST .../restore` для явности.

### 5.3 Блокировка изменения маршрута
- Существующий **`PUT/PATCH`** на обновление маршрута (если есть) или логика внутри `POST /api/v1/routes` при «upsert» — добавить проверку: при наличии `RouteRequest` для `id` — отказ с `ROUTE_LOCKED_BY_REQUEST`.

> Если в проекте сейчас только `POST` создания без update — блокировку реализовать на первом появлении endpoint редактирования; до этого момента фронт не даёт редактировать выбранный маршрут и предлагает «Дублировать».

## 6. Согласование с расчётом фрахта
- Создание заявки пользователем **не** требует сценария расчёта и не генерирует country breakdown.
- Расчёт коммерческой ставки через числовые сценарии и НБУ — см. `docs/specs/freight-cost-scenario-nbu-pricing.md` (отдельный шаг admin/manager после создания заявки).

## 7. Открытые вопросы (согласовать до кодирования)

### 7.1 Когда маршрут считается заблокированным
- **Вариант A (рекомендуется):** с первой **любой** `RouteRequest` для `routeId` (черновик/отправлена/отменена).
- **Вариант B:** только после перехода заявки в статус «принята в работу» / «не черновик».

Зафиксировать один вариант в реализации и в сообщениях UI.

### 7.2 Дублирование и активная заявка в черновике
Нужно ли разрешить пользователю иметь **две заявки** на один и тот же маршрут? Если нет — оставить как есть; если да — описать в отдельном ТЗ по статусам заявки.

### 7.3 Повторный `POST .../restore` (идемпотентность) — закрыто для v1
**Решение:** вариант **A** — при повторном вызове для уже **не удалённого** маршрута ответ **`200 OK`** и тот же DTO маршрута (безошибочные повторы, двойной клик, повтор запроса).

### 7.4 Чеклист закрытия открытых вопросов
Перед мержем реализации по данному ТЗ должны быть сняты пометки «открыто» в **§7.1–§7.2** (ответ в тексте спецификации или ADR). §7.3 закрыт.

## 8. Frontend (Angular Material)

Требования привязаны к экранам из раздела «Контекст UI»; компоненты Angular Material — по правилам проекта.

1. **`/route-builder`:** если маршрут **заблокирован** (есть заявка) — режим **только чтение** карты/точек (или редирект только на просмотр), основной CTA **«Дублировать и редактировать»** → `POST .../duplicate` → переход на редактор с **новым** `id` в query/route data.
2. **`/routes`:** переключатель **`view`** (`MatSelect` / `MatButtonToggleGroup`): «Активные», «Все», «Удалённые»; подсказки по soft delete; загрузка через `GET /routes/my?view=...`.
3. **`/routes`:** для строк в режиме «Удалённые» (и при необходимости в «Все») — действие **«Восстановить»** (`MatButton` / `MatMenu`) → `POST .../restore` → обновление списка; **`MatSnackBar`** при успехе.
4. **Диалоги** (`RouteFreightRequestDialogComponent` и др.): после успешной заявки не предлагать сохранить изменения в тот же snapshot; при ошибке **`ROUTE_LOCKED_BY_REQUEST`** — сообщение из i18n.
5. **`/my-freight-requests`** и **`/admin/route-requests`:** отображение пробега по странам только если данные пришли с бэка после явного расчёта (плейсхолдер/пустая таблица до шага из §3.3).

## 9. Критерии приёмки
- [ ] После создания `RouteRequest` для `routeId` любой API-запрос на изменение snapshot этого маршрута отклоняется с ожидаемым кодом и кодом ошибки.
- [ ] `POST .../duplicate` создаёт новый маршрут с новым `id`, копией данных, без заявок; новый маршрут редактируется штатно (в т.ч. в **`/route-builder`**).
- [ ] `GET /routes/my` без параметра и с `view=active` возвращает только **не удалённые** маршруты; `view=all` — не удалённые и удалённые; `view=deleted` — только удалённые; нет утечки чужих данных.
- [ ] Закрыты ответы по **§7.1–§7.2**; `POST .../restore` идемпотентен по §7.3.
- [ ] `POST /route-requests` не вызывает расчёт пробега по странам и не создаёт записи breakdown на этом шаге (проверка интеграционным тестом: нет вызова HERE для country split / нет строк в таблице breakdown, если такая есть).
- [ ] Документация OpenAPI/Swagger обновлена; e2e или integration тесты на дублирование и блокировку.

## 10. Миграция существующих данных
- Если в БД уже добавляли колонку `is_archived` до отмены требования — миграция **снятия**: удалить колонку или оставить всегда `false` и не использовать в API/UI (**предпочтительно удалить**, чтобы модель осталась двухсостоятельной: только soft delete).
- Маршруты, у которых уже есть заявки: считаются заблокированными с момента внедрения правила (логика через `EXISTS route_requests`).
